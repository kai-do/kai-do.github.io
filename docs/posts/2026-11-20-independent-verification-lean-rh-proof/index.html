What Is the Riemann Hypothesis?

Prime numbers (2, 3, 5, 7, 11, 13, …) are the building blocks of whole numbers: every whole number is a product of primes in exactly one way. They get rarer as numbers grow, but they never follow a simple pattern. Look at any stretch of numbers and the primes seem scattered almost at random.

In the 1790s, Gauss noticed that the number of primes up to any point follows a smooth curve surprisingly well. In 1859, Bernhard Riemann found a way to describe exactly how far the true count wanders from that curve. The errors are controlled by the zeros of a function now called the Riemann zeta function, written ζ(s). His hypothesis is that all of those zeros (apart from some easy ones at −2, −4, −6, …) sit on a single straight line, where the real part of s is ½. If that’s true, the primes are as evenly spread as they could possibly be. Their irregularity is like the static of a coin-flip sequence, never anything worse.

Why it matters:

  • It’s the most famous open problem in mathematics. It was on Hilbert’s 1900 list of the century’s key problems, and it is one of the Clay Institute’s seven Millennium Prize Problems, with a $1 million prize.
  • A lot of mathematics is built on it. Thousands of published results begin “assuming the Riemann Hypothesis…”. A proof would turn every one of them into a theorem.
  • It has resisted the best mathematicians for 167 years, despite checks of the first trillions of zeros, which all lie on the line.

(It wouldn’t break internet encryption, a common worry. That depends on how hard it is to factor large numbers, which this doesn’t change.)

What Happened

On 20 November 2026, Levent Alpöge posted a short remark and a 1.4 GB project written in Lean, claiming a proof of the Riemann Hypothesis, along with the same statement for every Dirichlet L-function (a whole family of close relatives of ζ). The proof was written with AI, and it is enormous: 175,187 files and about 17 million lines.

No person can read a proof that size. Lean is what makes it checkable anyway. Lean is a proof assistant: a program whose small core, the kernel, accepts a proof only if every single step follows from the rules of logic. That turns “is this proof right?” into a question anyone with a powerful enough computer can answer, as long as they’re careful about exactly what they check.

Within hours, people in the Lean community had built it and run it through several independent checkers (see the forum thread). The most complete public record is Andrew Sutherland’s page, which this page is modelled on.

Why I’m Checking It Myself

I wanted to do it end to end, for my own understanding, and to feel a small part of history being made.

I also have mixed feelings about it, and a lot of uncertainty about how AI will shape the future. Only weeks ago, in a Numberphile interview, I remember Terence Tao saying he didn’t expect the Riemann Hypothesis to be solved until around 2050. Now there is a claimed proof, written with AI, that Lean’s checkers accept. The only thing anyone can say with certainty is that nothing is off the table.

What a Check Can and Can’t Tell You

If every check passes, it means Lean’s kernel, and several independent checkers, accepted a proof of five exact formal statements, using nothing beyond Lean’s three standard axioms. It does not mean:

  • that anyone understands the proof. Understanding it is the work of mathematicians, and it will take years;
  • that the formal statements mean what we think. That is why they are spelled out in the next section;
  • that the checkers can’t all share one bug. They were written independently, in different languages, and some come with formal proofs of their own correctness, which makes a shared bug very unlikely.

The Five Statements

A proof is only as good as the statement it proves, so the check starts by pinning down exactly what has to be proved. It does that with two separate files.

  • The challenge is a short file that only states the five theorems. It doesn’t prove anything. Lean won’t accept a theorem without a proof attached, so each one ends in sorry, Lean’s placeholder for a proof left blank.
  • The solution is the project’s own Main.lean. It states theorems with the same five names and supplies the real proofs.

A checker then compares the two: the statements must mean exactly the same thing, and the proofs must be complete and accepted by the kernel.

Why a separate file? Building the project runs code the project contains, and that code can change what words mean inside it. Kevin Buzzard demonstrates this in talks by redefining exponentiation so that something that looks like Fermat’s Last Theorem becomes trivially “provable”. In the forum thread about this proof, someone showed that one line of notation can make RiemannHypothesis mean True. Reading the project’s own copy of the statements would not catch that. The challenge imports nothing but Mathlib, Lean’s shared math library, whose definition of the Riemann Hypothesis was written long before this project existed. It is built before any project code runs, so nothing in the project can tamper with it.

The five statements, in words:

Theorem In Words
riemannHypothesis Mathlib’s RiemannHypothesis: every zero of ζ other than −2, −4, −6, … (and the pole at 1) has real part ½.
riemannZeta_eq_zero_re The same statement, written out.
LFunction_ne_zero_of_half_lt_re For every modulus N and Dirichlet character χ, L(χ, s) ≠ 0 when Re s > ½, except at the pole χ = 1, s = 1.
LFunction_eq_zero_re Every zero of every Dirichlet L-function in the strip 0 < Re s < 1 has Re s = ½.
LFunction_eq_zero_re_of_isPrimitive The same, for primitive characters.
NoteThe challenge file in Lean 
import Mathlib

def RiemannZetaZerosOnLine : Prop :=
  ∀ s : ℂ, riemannZeta s = 0 → (¬∃ n : ℕ, s = -2 * ((n : ℂ) + 1)) → s ≠ 1 → s.re = 1 / 2

def DirichletLNonvanishingRightOfHalf : Prop :=
  ∀ (N : ℕ) [NeZero N] (χ : DirichletCharacter ℂ N) (s : ℂ),
    1 / 2 < s.re → (χ ≠ 1 ∨ s ≠ 1) → DirichletCharacter.LFunction χ s ≠ 0

def DirichletLZerosOnLine : Prop :=
  ∀ (N : ℕ) [NeZero N] (χ : DirichletCharacter ℂ N) (s : ℂ),
    0 < s.re → s.re < 1 → DirichletCharacter.LFunction χ s = 0 → s.re = 1 / 2

def PrimitiveDirichletLZerosOnLine : Prop :=
  ∀ (N : ℕ) [NeZero N] (χ : DirichletCharacter ℂ N), χ.IsPrimitive →
    ∀ s : ℂ, 0 < s.re → s.re < 1 → DirichletCharacter.LFunction χ s = 0 → s.re = 1 / 2

theorem riemannHypothesis : RiemannHypothesis := by sorry
theorem riemannZeta_eq_zero_re : RiemannZetaZerosOnLine := by sorry
theorem LFunction_ne_zero_of_half_lt_re : DirichletLNonvanishingRightOfHalf := by sorry
theorem LFunction_eq_zero_re : DirichletLZerosOnLine := by sorry
theorem LFunction_eq_zero_re_of_isPrimitive : PrimitiveDirichletLZerosOnLine := by sorry

I’m not a number theorist, so I don’t rely on my own reading of the last four. They have to match the project’s definitions term for term, which the checkers enforce, and they agree with the version reviewed in public by people who are.

Where this comes from. The challenge-and-solution setup isn’t mine. It is the Lean FRO’s Comparator model, which the community applied to this project in Deicyde/riemann-hypothesis; Kevin Buzzard’s post explains why each part matters. I wrote my challenge file independently, and apart from comments it is identical to the community’s Challenge.lean. It has to be: the statements are fixed by the project, and the checker requires them to match exactly. When I build their file with my Mathlib, it comes out byte for byte the same as theirs.

What this check adds. The challenge file only fixes what is checked. Everything around it is where this run goes further than the basic setup:

  • Sandboxed build in a fresh VM. The project is compiled with the network off, inside a Landlock sandbox that was tested before use, so the code that builds the proof can’t touch anything else.
  • Mathlib from source. Mathlib is compiled from source and compared file by file with its official build cache, so the check doesn’t rely on prebuilt files.
  • Nine checkers. Beyond Comparator’s Lean kernel and nanoda, the proof also goes to con-leche (including its --compare mode, a formally verified second implementation of the statement comparison), con-ron, lean4lean, Pestka and nanoclo.
  • Secondary checks. An axiom audit that walks every constant itself, a per-module kernel replay, and checks that no source file or tool changed during the run.
  • Hashes against other runs. My build and export are compared with the hashes other people published, so a match shows we checked the same bytes.

The formal proof itself doesn’t claim more than these five statements. Alpöge’s remark says the method should extend further, but the Lean project proves exactly these five, and those are what get checked.

What Happens Next

The project build takes roughly a day on this machine. After it come the export, then the checkers; the slowest, Lean’s own kernel replaying the full 61 GB proof on a single thread, may take another day or more. This page updates as each one reports. When the last result is in, I’ll write up what I found here, whatever it is.

How I Used AI

It felt right to check an AI-written proof with an AI’s help, and also strange. Claude (Anthropic’s AI) set up and ran this check with me: it wrote the scripts, ran the commands and drafted this page, and I reviewed and directed the work. That is exactly why the check is built so that no single party has to be trusted, including the AI running it. Every result here is read from logs, and the hashes let anyone confirm that the same bytes were checked. It doesn’t settle my mixed feelings about AI, but it does show one thing it can’t take away: a proof that anyone can check for themselves.

Technical Notes

How the Check Works

I treated the project as untrusted code. Building a Lean project runs code it contains (tactics, macros, build commands), so nothing from it ran on my own machine, and nothing that loads it ran outside a sandbox.

  1. A fresh virtual machine with its own kernel. Every tool is pinned to an exact commit and verified, and the project is downloaded and checked inside the VM.
  2. No network once the downloads are done. Mathlib is then compiled from source and compared file by file with Mathlib’s official build cache.
  3. The statements first. The challenge file is built and exported before any project code runs.
  4. A sandbox for the project. The build runs under Landlock via landrun: it can read its sources and the toolchain and write only its own build folder. Before starting, I tested that writes elsewhere, reading SSH keys and network connections all fail.
  5. Export, then judge. The compiled proof is exported to a single file, and the judges read only that file, so no project code runs while checking. lake comparator checks that the statements match the challenge and that only propext, Quot.sound and Classical.choice are used, then replays the whole proof through Lean’s kernel. Then the proof goes through every independent checker that fits in the VM’s memory.

Findings along the Way

NoteThe Checkers Catch a Missing Proof

Before trusting a “pass”, I checked that the tools can fail. The challenge file is all sorry, so I fed it to them as if it were a solution. Comparator rejected it in 34 seconds with error: Illegal axiom detected: 'sorryAx' (exit 1), and con-leche refused it with not implemented yet: use of the sorryAx axiom in value of riemannHypothesis. A missing proof can’t slip through either of them.

NoteWhy My Export’s Hash Differs from the Published One

My exported proof is 61,570,595,997 bytes; Andrew Sutherland’s is 209 bytes shorter, so the hashes differ. I downloaded his export (it matches his published hash) and compared the two. Listing every declaration in both, mine has exactly one his doesn’t, and none is missing: _private.Mathlib.Algebra.MvPolynomial.Rename.0.MvPolynomial.coeff_killCompl._simp_1_1. That is a helper theorem simp generates while elaborating a proof. In my build one proof happened to go through it; in his, the equivalent proof didn’t. Being a theorem, its proof is checked like everything else, so it can’t add an assumption. The first byte-level difference is of the same kind: an auto-generated bound-variable name, _hyg.155 in his export and _hyg.157 in mine, which Lean’s kernel ignores. The five statements are the same, which the checkers confirm against the same challenge.

NoteCompiled Files Match Only Partly; the Export Is the Real Comparison

My Main.olean and Statements.olean are byte-identical to the ones Andrew Sutherland published. Of all 175,187 compiled project files, 76,968 match his list and 98,219 don’t. I looked into why. My build is deterministic: recompiling a differing file gives the same bytes again, and so does compiling it against Mathlib’s official cache in place of my from-source Mathlib. But the bytes of a compiled .olean depend on exactly how Lean is invoked. Five different invocations of the same file, with and without Lake’s settings, gave five different hashes, and none matched his. His page says he called lean directly rather than lake build, and had only compared a 77-module sample against a real Lake build. So the .olean bytes aren’t a good fingerprint across build methods. The exported proof is closer: it contains only the declarations themselves (see the box above for how mine compares).

NoteMathlib from Source Matches the Official Cache, with One Exception

Of the 8,700 files in Mathlib’s official build cache, 8,689 are byte-identical to my from-source build. Ten belong to the cache tool itself and aren’t part of the math. One differs: Mathlib/Combinatorics/SimpleGraph/Walk/Operations.olean, and only in a single auto-generated lemma, SimpleGraph.Walk.take.eq_2. The other 230 constants in that file match. My build of it is deterministic (rebuilt twice, same bytes), so the cache’s copy was produced differently. Both versions are kernel-checked theorems; this is a reproducibility quirk, not a soundness problem.

NoteA Full Build Needs about 1.7 TB of Bookkeeping

For each module, Lake writes a .setup.json file listing everything it imports. Here that averages about 7 MB, and a sampled estimate over all 175,187 modules is about 1.7 TB. The files compress about 26× with zstd, so this run builds on a compressed btrfs disk.

NoteTwo Problems the Tests Caught

My sandbox wrapper first failed in a way that looked like success: the kernel supports Landlock ABI v6, landrun asked for v10 and refused to start, and every “access denied” test passed because nothing ran at all. A positive control (a command that must succeed) now runs first. Separately, the original checker script counted sorry warnings with the wrong quote characters, so that count could never be non-zero; it’s fixed. The axiom check was never affected.
